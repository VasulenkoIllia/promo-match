# Вимоги

З брифу клієнта (`brief/`, поза git) і слів власника, 2026-10-28. Без цін, персональних даних і секретів.

## Мета
Внутрішня система підбору сувенірної та промо-продукції (кружки, чашки, брелоки, сумки тощо). Клієнт приносить фото-референс чи опис того, що йому треба; система швидко знаходить той самий товар чи аналоги в постачальників і конкурентів, а ми прив'язуємо знайдене до свого товару.

Старт: демо (MVP) на 2 постачальниках, щоб перевірити, чи пошук за фото й описом справді працює і зручний. Якщо проєкт стартує, демо доробляємо чи переробляємо.

## Користувачі й ролі
- Співробітники, які підбирають товари під запит клієнта. Вхід за логіном.
- Адмін створює користувачів; самостійної реєстрації в демо немає.
- Ролей у демо немає: усі користувачі рівні, адмін це той, хто має доступ до сервера (рішення власника 2026-10-30). Ролі й права поза демо: відкрите питання 12.

## Функції
### Частина 1: постачальники (демо)
- Імпорт каталогів постачальників через їхні API, лише читання. Зараз 2, далі 5-20; товари різних постачальників можуть перетинатися й мати схожі характеристики.
- Пошук за фото-референсом, текстом або обома разом. Код моделі чи артикул постачальника в тексті дає точний збіг першим у списку (2026-10-30). Результат групується до моделі товару (кольори й інші варіації однієї моделі разом); фільтри за постачальником, категорією (спільний довідник для всіх постачальників, 2026-10-30), наявністю.
- Текстовий запит будь-якою мовою: перед пошуком переклад, поділ на окремі товари, коли лист просить кілька (2026-10-30), і виділення фільтрів (колір, матеріал, категорія, ціна). Фільтри з тексту лише пропонуються, пошук ними сам не звужується (2026-10-30, docs/integrations.md, «Claude API»).
- Свій товар: створити й прив'язати до нього товари постачальників з типом зв'язку «той самий» чи «аналог».
- Логін користувачів.
- Ранжування не залежить від постачальника: вектори, місця в списках і прочитаний запит, без квот і ваг постачальника; перевірка незалежним тестом (слова власника 2026-10-30, прочитаний запит у ранжуванні з 2026-10-31, README «Незалежний тест»).
- Тест якості пошуку: 20-50 реальних випадків (референс і правильна відповідь; для демо рішення власника 2026-10-30), частка випадків, де правильний товар у топ-10, окремо той самий товар і аналог. Порівнюємо модель ембедінгів; кольорове чи чорно-біле фото й обрізане до товару чи ні лише за словом власника. Як запускати: README, «Тест якості пошуку».

Порядок демо:
1. Smoke-тест API обох постачальників: логін, читання, зразки й структура відповідей локально, поза git.
2. Імпорт каталогів у БД: модель, варіант, фото, ціна, залишок, сирі відповіді окремо для дебагу.
3. Ембедінги фото й тексту товарів.
4. Пошук за фото, текстом чи обома, з фільтрами й групуванням до моделі.
5. Веб-інтерфейс: завантажити й обрізати фото, ввести опис, сітка результатів (фото, постачальник, ціна, залишок).
6. Свої товари і прив'язка результатів до них.
7. Логін.
8. Тест якості і висновок, чи реально.

Не в демо: конкуренти, AI-підбір, синхронізація за розкладом (у демо запуск вручну), нові постачальники.

### Частина 2: конкуренти
- Збір даних про ті самі товари з публічних сторінок сайтів конкурентів.
- Пошук за фото й параметрами по конкурентах, порівняння з товарами постачальників (зокрема цін), прив'язка до свого товару.

### Частина 3: AI-підбір
- AI-агент за запитом у вільній формі підбирає товари в постачальників і конкурентів з нашої БД, перевіряє наявність і пояснює вибір.

## Дані й обсяги
- 5-20 постачальників, 5-20 тис. товарів на кожного; товари мають варіанти (кольори тощо). Власник 2026-10-30: десятки постачальників, сотні тисяч товарів.
- Фото: в одного товару й варіанта їх може бути багато (в Axpol масив повних URL, у вибірці 5-12 на варіант). Вектори мають перші 3 фото кожного варіанта, 51 105 фото (рішення 2026-10-29, docs/decisions.md), пошук читає до 3 фото на модель (рішення 2026-10-30); модель даних дозволяє додати решту пізніше (фото окремими записами).
- Конкуренти: кількість і обсяг не відомі.
- Демо-каталоги в БД 2026-10-28: Axpol 3774 моделі, 10881 варіант, 71 тис. фото; Midocean 2786 моделей, 21738 варіантів, 37 тис. фото (docs/integrations.md, «Імпорт каталогів»).
- Векторів на повному обсязі: порядку 1-2 млн (оцінка, залежить від кількості фото в пошуку).
- Запропонована спільна модель:
  - джерело: постачальник чи конкурент;
  - модель товару: джерело, код моделі, назва, опис, категорія й матеріал кількома мовами, розміри, вага, країна походження, нанесення, сирі дані;
  - варіант: SKU, EAN, колір кількома мовами, ціна з валютою, залишок (є, резерв, наступна поставка, строк);
  - фото: модель, URL, порядок, стан обробки; варіанти, що показують фото, окремим зв'язком (у Midocean фото одного кольору спільне для всіх розмірів);
  - вектор: фото чи текст товару, назва моделі ембедінгів;
  - спільний довідник категорій: група й категорія з назвами uk і en, зіставлення повних шляхів категорій кожного джерела (docs/integrations.md, «Спільні категорії»);
  - свій товар (назва, артикул) і зв'язок «свій товар ↔ модель товару джерела» з типом «той самий» чи «аналог»; одна модель може бути прив'язана до кількох своїх товарів (рішення власника 2026-10-30);
  - користувачі, журнал синхронізацій.
- Ціни в різних валютах: Axpol PLN, Midocean EUR (перевірено smoke-тестом); Inspirion EUR, Blue Collection PLN (імпорт 2026-11-04).
- Закупівельні ціни конфіденційні: їх не комітимо ні у вивантаженнях, ні в дампах.
- Сховище: одна БД Postgres з розширенням pgvector (docs/decisions.md).

## Інтеграції
Контракт кожної: docs/integrations.md.
- Axpol B2B API: каталог, залишки, позиції й техніки нанесення.
- Midocean REST API: каталог, залишки, ціни товарів, дані нанесення, ціни нанесення.
- Модель ембедінгів для фото й тексту: обирається тестом якості.
- Claude API: розбір текстового запиту; у частині 3 агент підбору.
- Сайти конкурентів: частина 2.

## Нефункціональні
- API постачальників лише читаємо. Методи, що створюють замовлення чи макети, не реалізуємо й не викликаємо: вони створюють реальні замовлення. API бойові, sandbox немає.
- Дані постачальників беремо лише з API, їхні сайти не парсимо.
- Секрети тільки в `.env`.
- Вхід лише за логіном.
- Інтерфейс лише для комп'ютера (UI A).
- Мова пошуку й інтерфейсу не вирішена; часовий пояс не вказано.
- Бриф вимагає Node 18+ з вбудованим `fetch`; проєкт на Node 24.

## Поза обсягом
- Замовлення, макети, адреси доставки, методи оплати й доставки в API постачальників.
- Парсинг сайтів постачальників (сайти конкурентів збираємо в частині 2).

Axpol:
1. Закрито 2026-10-28 smoke-тестом: фото в масиві `Foto` повними URL `https://files.axpol.com/...` (docs/integrations.md).
2. Закрито 2026-10-28 імпортом: API зняті з продажу товари не позначає ні полем, ні методом. Імпорт щоразу читає повний каталог і позначає неактивним те, чого в ньому не стало (docs/integrations.md).

4. Закрито 2026-10-28 `--probe` і повним імпортом: `offset` рахує записи, `limit` до 1000 дотримано (більші не пробували), заголовків лімітів і 429 немає; імпорт бере сторінку 500.
5. Закрито 2026-10-28 smoke-тестом: актуальна адреса `https://axpol.com/api/b2b-api/`, стара відповідає 301.
